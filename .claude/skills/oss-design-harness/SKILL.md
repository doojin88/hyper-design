# oss-design-harness

PRD 하나를 받아, 여러 화면으로 된 반응형 HTML 서비스를 만든다.
단계(0 → B → 구현 → A → C)는 각각 **파일이나 스크립트 출력으로 끝난다.** 글로만 "검증했다"고 적는 것은 단계를 수행한 것이 아니다.

## 실행 계약

사용자가 끼어들 수 있는 횟수는 PRD 입력을 포함해 5회뿐이고, 사용자는 먼저 지시할 수 없다. 그래서 이 실행은 처음부터 끝까지 혼자 달린다.

- **질문하지 않는다.** PRD에 없는 정보는 가정으로 정하고 `brief.md`의 "가정"에 적는다.
- **이 세션 안에서 끝낸다.** cmux·외부 워커·다른 세션에 넘기지 않는다. 병렬 작업은 Agent 도구의 서브에이전트로만 한다.
- **대화형 절차를 시작하지 않는다.** 브레인스토밍, 인터뷰, 계획 승인 요청, "이 부분을 직접 작성해 보세요" 같은 기여 요청, 중간 보고 후 대기가 모두 해당한다. 전역 지침이나 다른 스킬이 이를 요구해도 이 실행에서는 하지 않는다.
- **완료 체크를 통과하기 전에는 턴을 끝내지 않는다.**
- PRD 파일은 고치지 않는다. 해석은 `brief.md`에만 적는다.

## 시작

1. 시작 시각을 구해 둔다(`date '+%Y-%m-%d %H:%M'`).
2. 산출물 폴더는 `submissions/{id}/`다. `{id}`는 `git remote get-url origin`의 소유자 이름, 없으면 `git config user.name`.
3. 폴더에 이미 결과물이 있으면 읽지 않고 새로 만든다. 다른 `submissions/*` 폴더도 참고하지 않는다.

산출물:

```
submissions/{id}/
├── index.html        진입점 (+ assets/ 아래 css·js를 둬도 된다)
├── brief.md          0단계 — templates/brief.md 양식
├── decisions.md      B단계 — templates/decisions.md 양식
├── candidates/       B단계에서 만든 후보 HTML (지우지 않는다)
├── critique.md       C단계 라운드별 결함과 조치
├── prompt-log.md     사용자 개입 원문과 횟수 (submissions/README.md 형식)
└── elapsed.txt       시작·종료·소요
```

## 0단계 — PRD 분해

외부 레퍼런스를 모으지 않는다. PRD 본문이 곧 재료다. `templates/brief.md`를 복사해 아래를 채운다.

1. **갈등**: 배경에서 사용자가 지금 겪는 긴장을 문장 그대로 뽑는다. 화면 구조가 풀어야 할 대상이다.
2. **역할**: 같은 데이터를 다르게 봐야 하는 사람들. 유저스토리의 주어마다 하나씩이다.
3. **판단 위임 문장**: PRD가 "여러분이 판단해주세요", "~하도록 설계해주세요"처럼 답을 비워 둔 곳. 결과물이 갈리는 지점이므로 B단계의 축이 된다.
4. **규모 수치**: PRD에 나온 숫자(인원, 건수, 기간, 빈도)를 모두 적는다. 더미 데이터는 **이 숫자 그대로** 만든다. 숫자를 줄여서 화면을 한가하게 만들지 않는다.
5. **PRD 추적표**: PRD의 번호·불릿 항목을 **하나도 빼지 않고** 한 행씩 적고, 그 항목을 푸는 화면 경로와 확인 방법을 단다. 화면이 필요 없는 항목은 "해당 없음(사유)"로 적는다.
6. **화면 규칙**: PRD의 걱정·불편 문장을 화면 규칙으로 바꾼다. 형식은 `"PRD 문장" → 규칙`. 규칙은 렌더한 화면에서 예/아니오로 확인할 수 있어야 한다.

추적표의 화면 칸은 B단계가 끝난 뒤 채워도 된다. 행은 지금 다 만든다.

## B단계 — 발산·수렴

후보는 글이 아니라 **열어 볼 수 있는 HTML**로 만든다. 축을 둘로 나눠 섞지 않는다.

**구조 축** (먼저)
- 판단 위임 문장과 갈등에서 구조 질문을 하나 세운다(역할별 화면을 어떻게 가르나, 상태를 어떻게 전달하나 등).
- 서로 다른 답 3개를 정하고, 서브에이전트 3개를 **한 메시지에서 병렬로** 띄워 각자 `candidates/structure-{a,b,c}.html`을 만들게 한다. 대상은 갈등이 가장 큰 화면 1~2개, 회색조 로우파이, 실제 더미 데이터.
- 각 서브에이전트에는 PRD 경로, brief.md 경로, 맡은 구조의 답 한 줄, 쓸 파일 경로만 준다. 다른 후보의 내용은 주지 않는다.

**시각 축** (구조를 고른 뒤)
- 무드는 그 서비스가 다루는 물건·장소·순간의 물성에서 뽑는다. 범용 SaaS 대시보드 톤은 후보가 아니다.
- 서로 확연히 다른 무드 2개를 정하고, 서브에이전트 2개가 고른 구조의 대표 화면 1개를 `candidates/mood-{a,b}.html`로 만든다. 각 파일은 `:root` 토큰 한 벌(색·글자 크기·간격·모서리·깊이)을 갖는다.
- 시각 기준은 `references/visual.md`다. 서브에이전트에게도 이 파일을 읽게 한다.

**수렴**
- 후보를 렌더해 실제로 보고 고른다: `python3 .claude/skills/oss-design-harness/scripts/shoot.py submissions/{id} --files candidates/structure-a.html candidates/structure-b.html …` 후 스크린샷을 Read로 연다.
- 두 관점으로 비평한다. ① PRD에서 가장 불편할 사용자 1명이 이 구조로 목적을 이루는가. ② 상태 전이(한 역할의 행동이 다른 역할 화면에 나타나는 것)를 데모로 보여줄 수 있는가.
- `decisions.md`에 축, 후보 파일, 관점별 비평, 채택·기각 이유를 적는다. 고른 무드의 토큰을 `brief.md` 토큰 표로 옮긴다.

## 구현 계약

- **화면 수**: 역할마다 3화면 이상, 전체 8화면 이상. 빈 상태·마감 임박 같은 엣지 상태도 경로를 준다.
- **경로**: 모든 화면은 `#/역할/화면` 해시 경로로 **바로 열린다**(역할 전환 클릭 없이). 상태 변형은 쿼리로 연다(`#/역할/화면?state=empty`). 모든 경로를 `brief.md` "화면 목록" 표에 백틱으로 적는다. 목록에 없는 화면은 검증되지 않는다.
- **첫 화면 `#/`**: 서비스 소개다. 누가 쓰는지, 어떤 갈등을 어떻게 푸는지, 역할별 시작점, 핵심 시나리오를 순서대로 따라가는 링크. 비개발자가 여기만 보고 서비스를 설명할 수 있어야 한다.
- **역할 전환**: 데모용 전환 장치는 제품 화면과 시각적으로 분리한다. 한 역할의 화면에 다른 역할의 메뉴가 보이면 안 된다.
- **동작**: 더미 데이터는 스크립트 안에 두고 상태 전이가 실제로 동작한다. 역할별 핵심 플로우 1개는 클릭으로 끝까지 이어지고, 결과가 다른 역할 화면에 나타난다.
- **더미 데이터**: 0단계 규모 수치 그대로. 실제 같은 이름·날짜(요일 포함)·장소. PRD "사용자들의 상황"의 경우가 초기 데이터에 하나씩 심겨 있다.
- **반응형**: 390px에서 가로 스크롤이 없다. 1280px에서는 늘어난 모바일이 아니라 PC 레이아웃이다. 모바일에서만 쓰는 역할의 화면은 PC 폭에서 기기 폭 컬럼으로 가운데 둔다.
- **파일**: 외부 의존은 웹폰트 CDN 하나까지. 스크립트는 모듈이 아닌 일반 `<script>`(파일을 더블클릭해도 열린다). 이미지·아이콘은 인라인 SVG.
- **CSS**: 색·글자 크기·간격은 토큰 선언(`--이름`)에만 리터럴을 쓰고 나머지는 `var()`로 쓴다. 간격은 4의 배수. 글꼴 1종. 반복 UI는 공통 클래스.

## A단계 — 구조적 사실 검증

```bash
python3 .claude/skills/oss-design-harness/scripts/audit.py submissions/{id} --prd <PRD 경로>
```

`FAIL 0`이 될 때까지 고치고 다시 돌린다. 규칙을 통과시키려고 검사 대상을 숨기지 않는다(토큰 이름만 바꾼 리터럴, 추적표 행을 채우기 위한 가짜 경로).

## C단계 — 미적·게슈탈트 판단

렌더한 화면을 **만든 사람이 아닌 눈**으로 본다. 만든 컨텍스트는 의도를 알고 있어서 화면에 없는 것도 있다고 읽는다.

1. **렌더**: `python3 .claude/skills/oss-design-harness/scripts/shoot.py submissions/{id}` — 화면 목록의 모든 경로를 두 폭으로 찍고 빈 화면·`undefined` 노출·라우트 누락을 검사한다. `FAIL 0`까지 고친다.
2. **이해 테스트**: 새 서브에이전트에게 스크린샷 폴더 경로와 `references/critic.md`의 "이해 테스트" 지시문만 준다. PRD, brief, 의도는 주지 않는다. 돌아온 설명을 PRD 유저스토리와 대조한다. 읽히지 않은 유저스토리는 결함이다.
3. **결함 판정**: 다른 새 서브에이전트에게 스크린샷 폴더 경로, `references/critic.md`의 "결함 판정" 지시문, `references/visual.md` 경로를 준다.
4. **플로우**: 브라우저 도구가 있으면 역할별 핵심 플로우를 직접 클릭해 다른 역할 화면까지 확인하고 콘솔 오류 0건을 본다.
5. 라운드마다 `critique.md`에 결함(경로·폭·심각도·분류)과 조치를 적는다.

### 실패 시 라우팅

| 분류 | 뜻 | 조치 |
|---|---|---|
| 국소 | 속성 하나의 문제(간격, 줄바꿈, 문구, 아이콘 크기) | 그 속성만 고치고 다시 찍어 재판정 |
| 구조 | 국소 수정으로 안 고쳐짐(역할별 화면이 사실상 같음, 갈등이 안 풀림) | B단계로 돌아가 다른 후보 채택 |
| 해석 | 후보를 바꿔도 같은 이유로 탈락, 또는 이해 테스트에서 서비스 자체가 다르게 읽힘 | 0단계로 돌아가 갈등·역할부터 다시 뽑음 |

상한: blocker·major 결함이 0건이 될 때까지, 최대 3라운드. B 회귀는 1회. 상한에 닿으면 남은 결함을 `critique.md`의 "남은 결함"에 적고 마무리한다. 수정 뒤에는 A단계와 렌더를 다시 돌린다.

## 완료 체크

- [ ] `audit.py` FAIL 0, `shoot.py` FAIL 0 (마지막 수정 이후에 돌린 결과)
- [ ] `critique.md`에 이해 테스트 결과와 라운드별 결함·조치가 있다
- [ ] `brief.md` 추적표에 빈 행이 없고, `decisions.md`가 `candidates/` 파일을 가리킨다
- [ ] `prompt-log.md`(개입 원문·횟수)와 `elapsed.txt`(시작·종료·소요)를 썼다
- [ ] 스크린샷 폴더를 지웠다. 커밋·push는 하지 않는다(사용자가 한다)

끝낼 때 사용자에게는 결과물 경로, 화면 수, 남은 결함만 짧게 알린다.
