# oss-design-harness

현업 디자이너의 판단 기준을 추출해, 실제 화면을 HTML로 만드는 하네스.
두 번의 시험 실행(청첩장모임·가족여행)에서 실제로 막혔던 지점을 기준으로 채웠다.

순서를 그대로 따라가는 것이 아니라, 아래 4단계가 각각 무엇을 판단해야 하는지에 집중한다.

## 운영 원칙 (하네스톤 규칙과 맞물리는 것)

- **사용자 개입은 5회 이하다.** PRD 입력이 1회다. 질문은 꼭 필요한 것만, 한 번에 모아서 묻는다.
- **질문 대신 가정을 쓴다.** 되묻는 대신 "이렇게 가정했습니다"를 `brief.md`에 남기고 진행한다. 가정이 틀렸을 때 사람이 고칠 수 있게 하면 충분하다.
- **결과물은 `submissions/{id}/`에 둔다.** `index.html`(진입점), `brief.md`, `prompt-log.md`, `elapsed.txt`. 시작·종료 시각은 처음과 끝에 기록해 둔다.
- **PRD는 수정하지 않는다.** 그대로 읽고, 해석은 `brief.md`에만 적는다.
- 검증용 서버·스크린샷 등 임시 산출물은 끝나면 정리한다. 레포에 남기지 않는다.

## 0단계 — 요구사항 정렬

화면을 만들기 전, 무엇을 만들어야 하는지 자체가 불확실할 때 실행한다. PRD가 명확하면 짧게 끝낸다.

- **레퍼런스/시나리오 소싱 방법**: 외부 앱 스크린샷을 모으지 않는다. PRD 본문에서 아래 셋을 뽑는 것이 곧 소싱이다.
  1. **갈등**: PRD 배경에 "서로 배려하다 정보가 안 간다", "방이 수십 개로 늘어 놓친다"처럼 적힌 긴장 (예: 가족여행 = 자녀는 미완성을 고치고 싶고 부모는 확정된 흐름만 보고 싶다).
  2. **역할**: 같은 데이터를 다르게 봐야 하는 사람들 (계획자/확인자, 예비신랑/예비신부/초대받은 지인).
  3. **평가 문장**: PRD가 "여러분이 판단해주세요"라고 넘긴 부분. 여기가 심사에서 갈리는 지점이다.
  기존 서비스를 참고하되, 갈등을 실제로 푸는 구조인지가 기준이다. "기존 앱과 비슷하다"는 감점 신호다.
- **질문 형식**: 라벨형 질문("모던한 게 좋으세요?") 금지. 꼭 물어야 하면 두 안을 구체적 장면으로 보여주고 "좋다/싫다 + 이유"를 받는다. 개입 횟수가 아까우므로 기본값은 묻지 않는 것이다.
- **판단기준 역추출 방법**: PRD의 걱정·불편 문장을 "화면 규칙"으로 바꾼다.
  - "부모가 오히려 신경 쓰거나 귀찮아할까 봐" → 규칙: 후보 편집은 알림을 만들지 않는다.
  - "여러 단계를 거치는 조작을 답답해한다" → 규칙: 부모 화면은 탭 3개 이하, 한 화면 한 목적, 확인은 버튼 한 번.
  - "어느 방에서 무슨 얘기가 오갔는지 놓친다" → 규칙: 상태(대기/확정대기/확정/완료)를 화면의 1차 축으로 둔다.
- **가정 처리**: 확정 안 된 정보(기준일, 더미 인물, 플랫폼, 데이터 저장 여부)는 `brief.md`에 "이렇게 가정했습니다"로 명시한다.
- **산출물**: `brief.md` (템플릿: `templates/brief.md`). 반드시 다음을 포함한다: 설계 원칙(갈등→구조 3~4줄), 가정, 화면 목록, 디자인 토큰.

## B단계 — 발산·수렴

무엇을 만들지는 정해졌으나 어떻게 만들지 정답이 하나가 아닐 때 실행한다.

- **독립 축 식별**: 이 하네스에서 기본으로 나누는 축은 넷이다. 프로젝트마다 다시 확인한다.
  1. **정보 구조**: 역할별 뷰를 어떻게 가르는가 (같은 화면의 필터 / 완전히 다른 화면 / 미리보기 전환).
  2. **상태·알림 정책**: 무엇이 언제 누구에게 전달되는가 (즉시 / 묶음 / 요청 시).
  3. **밀도·접근성**: 사용자 세대·상황에 맞는 글씨 크기, 탭 개수, 한 화면 정보량.
  4. **비주얼 무드**: 색·톤·모서리. 가장 마지막에 정한다. 앞의 셋보다 판별력이 낮다.
- **후보 생성 방식**: 축 1·2는 후보를 2~3개씩 서술로 뽑는다(코드 작성 전). 서술만으로 승부가 나지 않을 때만 로우파이 HTML을 만든다. 축 4는 후보 없이 토큰 한 벌로 확정해도 된다. 병렬 서브에이전트가 가능하면 축마다 하나씩 배정한다.
- **비교·수렴 방식**: 최소 두 관점으로 교차 비평한다.
  - **PRD 사용자 관점**: 가장 불편한 사용자 1명(예: 67세 부모, 응답을 미루는 지인)이 이 구조로 목적을 이룰 수 있는가.
  - **구현·검증 관점**: 단일 HTML에서 상태 전이(확정→알림→수신)를 실제로 시연할 수 있는가. 시연 불가한 구조는 감점한다.
- **산출물**: `decisions.md` (템플릿: `templates/decisions.md`). 채택안·기각안·기각 이유를 한 줄씩.

### 구현 지침 (B→A 사이)

- 페이지 수: 비개발자가 서비스를 이해할 만큼. 핵심 역할별로 **최소 3~4화면씩**, 전체 7화면 이상.
- 형태: 해시 라우팅 단일 `index.html`(외부 의존은 웹폰트 CDN 하나까지). 데이터는 스크립트 안 더미로 두고, 상태 전이가 **실제로 동작**하게 한다. 화면만 있고 눌러도 아무 일 없는 결과물은 쓰지 않는다.
- **역할 전환 바**(데모용)를 상단에 둔다. 심사자가 한 화면에서 모든 역할 시점을 볼 수 있어야 한다.
- 더미 데이터는 실제처럼 쓴다(이름·날짜·장소). 갈등 상황(일정 겹침, 미회신, 미확정)이 초기 화면에 이미 드러나게 심는다.
- 모바일 우선 반응형: 390px에서 가로 스크롤이 없어야 하고, PC(1280px)에서는 계획하는 쪽 화면이 사이드바 레이아웃으로 바뀐다.

## A단계 — 구조적 사실 검증

화면이 다 만들어진 뒤, 데이터로 예/아니오 또는 수치로 검증한다. 스크린샷 없이 HTML/CSS 코드(요소·스타일 값)만으로 확인 가능.

체크 카테고리 (항목은 고정, 기준값은 프로젝트마다 `brief.md`에서 캘리브레이션):

- [ ] 컬러 팔레트 일관성 — 모든 색은 `:root` CSS 변수(토큰)로 선언하고 본문 CSS는 변수만 쓴다. 허용 값은 `brief.md` 토큰 표. 임의 hex 직접 사용은 예외 목록에 적는다.
- [ ] 타이포 스타일 재사용 — 폰트 패밀리 1개, 제목 3단계 이하, 본문 크기는 변수(`--fs`)로 뺀다. 접근성 대상 사용자(고령 등) 화면은 본문 18px 이상.
- [ ] Spacing 그리드 준수 — 4pt 단위 토큰(4/8/12/16/24/32). 그 밖의 여백 값은 예외로 표시.
- [ ] 컴포넌트 재사용률 — 카드·칩·버튼·리스트 행은 공통 클래스(`.card` `.chip` `.btn`)로 만들고, 같은 UI를 화면마다 새로 스타일링하지 않는다.
- [ ] 요소·클래스 네이밍 semantic 여부 — 역할·의미로 짓는다(`.banner` `.todo`). 외형으로 짓지 않는다(`.red-box`). 버튼은 `<button>`, 링크는 `<a>`, 이동 메뉴는 `<nav>`.
- [ ] UI 상태 커버리지 — hover·`:focus-visible`·disabled·empty(빈 상태 문구)·토스트(액션 결과 피드백)가 있는가. 터치 타깃 44px 이상.
- [ ] 실행 검증 — 인라인 스크립트 `node --check` 통과, 브라우저 콘솔 오류 0건(favicon 404 제외).
- [ ] 상태 전이 시연 — 핵심 플로우 1개를 클릭으로 끝까지 실행해 결과가 다른 역할 화면에 나타나는지 확인.

## C단계 — 미적·게슈탈트 판단

화면이 다 만들어진 뒤, 반드시 스크린샷을 렌더해서 실제로 봐야 판단한다. 데이터 조회로 대체 불가.

**절차**: 로컬 정적 서버로 띄운다(`file:` 프로토콜은 브라우저 도구가 막는다). 데스크톱 1280×800과 모바일 390×844 두 폭에서 역할별 대표 화면과 핵심 플로우 이후 화면을 찍는다. 해시 라우팅은 페이지를 다시 불러오지 않으므로, 코드 수정 후 재검증할 땐 쿼리(`?v=2`)를 붙여 새로 불러온다. 스크린샷·서버는 검증이 끝나면 지운다.

체크 항목 (시험 실행에서 실제로 잡힌 결함을 근거로 구체화):

- [ ] 섹션 간 색온도·조명 일관성 — 화면 전체가 토큰 팔레트 한 벌의 톤(따뜻한 종이색 배경 등)을 유지하는가. 카드마다 흰색·회색·베이지가 섞이면 실패.
- [ ] 시각적 위계가 한눈에 읽히는가 — 화면당 1차 액션은 1개(색이 채워진 버튼). 3초 안에 "지금 내가 할 일"이 보이는가. 경고·알림 띠는 화면당 상단에 한 종류만.
- [ ] 여백 리듬의 체감 일관성 — 섹션 간격 > 카드 내부 간격 > 요소 간격 순으로 항상 커야 한다. 같은 종류 카드는 어느 화면에서나 같은 간격.
- [ ] 정보 밀도 번잡함 여부 — 고령·비전문가 사용자 화면은 요약 카드에 최대 3줄, 나머지는 "외 n개". 계획자 화면만 밀도를 높인다.
- [ ] 클리셰/AI슬롭 여부 — 보라·파랑 그라데이션, 이유 없는 이모지 남발, "지금 시작하세요" 류 문구, 의미 없는 통계 카드는 실패. 문구는 그 서비스의 상황어로 쓴다.
- [ ] 엣지케이스(빈 상태 등)의 실제 완성도 — 빈 목록마다 "무엇이 없는지 + 다음 행동"이 있는가.
- [ ] **역할 경계 누수** — 다른 역할의 메뉴·정보가 보이면 실패(예: 초대받은 지인 화면에 신랑·신부 탭바). 역할 전환 후 각 화면 상단·하단을 확인한다.
- [ ] **글자 줄바꿈** — 큰 글씨 모드에서 한 단어가 어색하게 잘리지 않는가(예: "금요/일"). 긴 날짜·이름은 줄을 직접 나눈다.
- [ ] **아이콘·요소 크기** — 아이콘이 부모 크기를 무시하고 비대해지지 않는가(svg는 반드시 폭·높이 규칙을 둔다).
- [ ] **의미 없는 약어** — 접두어·축약이 사용자에게 뜻이 통하는가("점/저" 같은 첫 글자 축약 금지).
- [ ] **한국어 문구** — 조사를 "이(가)", "(으)로"처럼 병기하지 않는다. 받침 판단이 어려우면 조사가 필요 없는 문형으로 쓴다("~ 확정됐어요").

### C단계 실패 시 라우팅

원인을 진단해서 아래 셋 중 하나로 분기한다.

1. **국소적 결함** (표면 속성 하나의 문제) → 그 속성만 고쳐 C단계 재검. B단계로 돌아가지 않는다. (예: 아이콘 크기, 줄바꿈, 문구)
2. **방향 자체가 틀림** (국소 조정으로 안 고쳐지는 구조적 문제) → B단계로 회귀, 다른 후보 선택 또는 재발산. (예: 역할별 뷰가 사실상 같은 화면, 알림 정책이 갈등을 못 풀음)
3. **반복 실패** (B단계에서 후보를 바꿔도 같은 이유로 계속 탈락) → 0단계로 에스컬레이션. PRD 해석(갈등·역할)부터 다시 본다.

재시도 상한: 국소 수정은 라운드당 결함 묶음 1회, 최대 3라운드. B 회귀는 1회. 상한 초과 시 사람에게 에스컬레이션. 최종 "이 정도면 됐다" 판단은 항상 사람이 내린다.
